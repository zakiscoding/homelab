# Postmortem: WSL down for 9 days on the GPU PC's Windows boot

[homelab](../../README.md) / [docs](../README.md) / postmortems · Blameless format · Written 2026-11-14

| | |
|---|---|
| **Duration** | 2026-11-04 → 2026-11-13, about 9 days |
| **Detected** | 2026-11-13, by hand: someone noticed while doing other work. No alert fired |
| **Impact** | The WSL2 copy of vLLM, its Prometheus/Grafana/DCGM monitoring and the `cloudflared` tunnel were down on the GPU PC's Windows boot. Chat kept answering, but not from the GPU: the public gateway served Workers AI's fallback model, and the iMac API fell back to Ollama. GPU metrics for those 9 days are missing |
| **Severity** | Degraded, not down: every request got an answer, which is exactly why nobody noticed |

## Timeline (Eastern)

| When | What |
|---|---|
| 2026-10-27 | Last reboot of the GPU PC (Windows). The `WSL Keep Alive` scheduled task starts at boot and holds a WSL session open, so the distro and its containers stay up |
| 2026-11-04 | The task's session ends with exit code 1, probably from a WSL shutdown or update. With no session left, WSL stops within seconds, taking vLLM, the tunnel and the monitoring stack with it |
| 2026-11-04 → 11-13 | Chat answers from the fallbacks. Gateway responses carry `x-gateway-backend: workers-ai`, which nobody is watching. The WSL Prometheus is down along with what it monitors, and the iMac's central monitoring didn't exist yet |
| 2026-11-13 | Found by hand. WSL restarted; tunnel, vLLM and monitoring come back. The keep-alive task gets a second trigger every 5 minutes with `MultipleInstances=IgnoreNew`, and `.wslconfig` gets `vmIdleTimeout=-1` |
| 2026-11-13 | iMac Prometheus becomes the homelab's central monitoring: it federates the GPU PC's Prometheus over the tailnet, so a dead GPU PC stack shows up as a down target instead of silence |
| 2026-11-14 | SLOs and alerts added (below), with a rule test that replays this outage |

## Root cause

WSL2 stops a distro seconds after its last session closes, even with Docker containers set to
`restart: unless-stopped`. Uptime depended on one long-lived session started by a task whose only
trigger was **system boot**. When that session ended without a reboot, nothing restarted it.

## Why it took 9 days to notice

1. **Graceful degradation hid the failure.** Both chat paths had fallbacks, and those fallbacks kept
   working. The system's availability was fine; its *quality* wasn't (a smaller model, not the GPU).
2. **The monitor died with the thing it monitored.** The only Prometheus watching vLLM ran inside the
   same WSL distro.
3. **No alerting existed**, and nothing measured "answered by the GPU" as a target.

## What changed

| Action | Status |
|---|---|
| Keep-alive task restarts a dead session within 5 minutes (`IgnoreNew` makes it a no-op while healthy) | Done 2026-11-13 |
| `vmIdleTimeout=-1` in `.wslconfig` | Done 2026-11-13 |
| Central monitoring on the iMac, outside the failure domain | Done 2026-11-13 |
| SLO **chat-on-gpu**: a synthetic probe every 15 s of which backend the API uses, 95% target; pages within 30 minutes of a full fallback ([rule test](https://github.com/zakiscoding/homelab-services/blob/main/prometheus/tests/alerts.test.yml)) | Done 2026-11-14 |
| SLO **gateway-chat-on-gpu**: the gateway's own trace spans; share of chat answered by Workers AI | Done 2026-11-14 |
| Alert **GpuPcWslDown**: Windows boot reachable, vLLM on it down for 15 minutes. Replayed in a rule test (fires at 16 min; silent when the PC is off or in its Ubuntu boot) | Rules done. The live "Windows is up" probe needs `tailscale serve --tcp 2222` on Windows, see below |
| Alerts reach a phone (Alertmanager → ntfy) | Done 2026-11-14 |
| Test that the 5-minute trigger really restarts the session, and a cold Windows reboot | Open |

## What went well

- The fallbacks did their job: no user-visible errors for 9 days.
- The fix was small and is documented where the next person will look
  ([gpu-systems-lab CLOUDFLARE.md](https://github.com/zakiscoding/gpu-systems-lab/blob/main/docs/CLOUDFLARE.md#running-on-the-gpu-pc)).

## What went badly, and a new finding

- Fallback health was never measured, so "degraded" looked like "fine".
- While deploying the new monitoring on 2026-11-14, the first traced chat request showed a second
  silent degradation of the same kind. The iMac API had again fallen back, this time because:
  - containers in the iMac's Colima VM reach the tailnet only about 1 time in 3 (the host: 20/20);
  - the API's 2-second backend probe therefore usually fails;
  - the Ollama fallback it then uses times out after 133 s.

  The new `chat-on-gpu` SLO paged on it within the hour. The fix is a Colima networking change with
  iMac downtime. It is tracked in homelab-services
  [docs/OBSERVABILITY-SLO.md](https://github.com/zakiscoding/homelab-services/blob/main/docs/OBSERVABILITY-SLO.md#what-the-traces-found-on-day-one).

## Lessons

- **A fallback is a failure mode, not a success.** Measure how often it is used, and set a target.
- **Put the monitor outside the failure domain** of what it watches.
- **Uptime that depends on a one-shot trigger needs a periodic one.** If something must always run,
  "start at boot" isn't enough.
